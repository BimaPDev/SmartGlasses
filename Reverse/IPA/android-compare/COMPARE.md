# iOS vs Android — MYVU AR 1.1.28 (iOS) vs MYVU AR 2.40.51 intl (Android)

Sides compared: iOS `com.upuphone.overseas` v1.1.28 (`Reverse/IPA/extracted/Payload/XJOverSeas.app`)
vs Android `com.upuphone.star.launcher.intl` v2.40.51 (`Reverse/extracted/`, per `Reverse/FINDINGS.md`).
Supplementary-only reference: `Reverse/extracted2/` is a **different** Android build —
domestic China `com.upuphone.star.launcher` v2.49.24, reinforced/Ijiami-protected
(`Reverse/FINDINGS_2.49.24.md`) — cited only where it clarifies an intl-vs-domestic split,
never as the primary Android comparator.

## FairPlay limitation (governs every row below)

The iOS main binary `XJOverSeas` and the Flutter AOT payload `Frameworks/App.framework/App`,
plus all 99 embedded `.framework` binaries, measure `LC_ENCRYPTION_INFO_64` `cryptid 1`
(`Reverse/IPA/recon/RECON.md`) — Apple **FairPlay** DRM. Their `__TEXT` segments cannot be
disassembled or class-dumped from this App-Store IPA; only unencrypted plists, `.bundle`
resources, `flutter_assets`, `.lproj` strings, and `__LINKEDIT` symbol tables are readable.
The Android side is Flutter + Dalvik: `Reverse/extracted/` is a plain jadx-decompiled APK
with fully readable Java/Kotlin (`Reverse/FINDINGS.md`, `Reverse/MYVU_cloud_API_map.md`
read `NetConfig.java`, `SignUtils.smali` etc. directly), so most of the asymmetry below is
structural, not incidental: Android evidence is source-level (class/method names, literal
hardcoded hosts, signing formulas); iOS evidence is resource-level only (framework names,
bundle IDs, plist keys, plaintext HTML/strings). No decrypted iOS native code is claimed
anywhere in this report.

## Overseas-vs-domestic and version-gap caveats

The Android side used for this comparison, `Reverse/extracted/` (v2.40.51, `com.upuphone.star.launcher.intl`), is itself the international/overseas Android build — the closest available Android counterpart to the iOS "OverSeas" bundle. A second, much newer Android artifact exists at `Reverse/extracted2/` (v2.49.24, `com.upuphone.star.launcher`, domestic China, Ijiami-reinforced per `Reverse/FINDINGS_2.49.24.md`) and was used above only to confirm that AMap is a domestic-only native SDK swap, never as the primary Android comparator — mixing it in directly would conflate an ~9-minor-version gap and an intl/domestic product split with a same-generation diff. No equivalent newer iOS build was available to check against 2.49.24, so the ~9-version Android gap (2.40.51 → 2.49.24) cannot be cross-checked against any matching iOS release; some Android findings cited from `Reverse/FINDINGS.md`/`Reverse/MYVU_cloud_API_map.md` may have drifted by the time of iOS 1.1.28's release.

## Conclusion

The two apps share one architecture at the framework level: both are Flutter-add-to-app products from the same Xingji Meizu/Flyme ecosystem, both embed the identical third-party BLE stack (flutter_blue_plus + ble2301 + Nordic DFU) for talking to the same glasses/ring hardware, both link HERE as the sole native maps SDK on their overseas/intl builds (with AMap demoted to compliance-text-only or absent entirely outside China), and both center identity on a Flyme/Meizu account with GeeTest captcha and dormant Lark/Feishu SSO resources bundled alongside it. The clearest genuine differences are: (1) analytics/crash vendor choice — Amplitude+Firebase(disabled)/KSCrash on iOS vs Bugly+first-party xr-datatrack telemetry on Android; and (2) the assistant pipeline — iOS ships a real on-device offline ASR/VAD/NLG bundle (~56MB of ONNX models) as a fallback to cloud AI, while the documented Android path is cloud-only. Everything at the `myvu.cn` cloud-backend layer (OTA signing, config gateway, ASR/AI hosts) is fully readable on Android but completely invisible on iOS due to FairPlay — those rows are marked "cannot confirm" rather than guessed at.
