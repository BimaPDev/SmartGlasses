## 1. The memory map (this is the root cause of most errors below)

`platform_tester.bin` (1.0.12.83, `0x6753FC`) has **three** regions, not one flat base:

| File range | Runtime | Contents |
|---|---|---|
| `0x000000`–`0x0283F4` | XIP flash `0x2C010000`+ | early boot, pre-PSRAM |
| `0x0283F4`–`0x469954` | **copied to PSRAM `0x3C000000`** | ALL rodata/strings, both sub-images, LVGL assets, audio |
| `0x469954`–`0x6753FC` | XIP flash `0x2C479954`+ | bulk of M55 `.text` |

**`0x3C000000 − 0x283F4 = 0x3BFD7C0C`.** The "TRACE remap" constant in `ADDRESS_AUDIT.md` was
never a trace-string quirk — it is the PSRAM copy destination. Code uses `file + 0x2C010000`;
data uses `file + 0x3BFD7C0C`; the `0x283F4` seam is why they differ.

### The M55 base is `0x2C010000`, not `0x2C000000`

`ADDRESS_AUDIT.md`'s headline rule is off by `0x10000`; its own vtable footnote is right.
Three independent proofs:

1. **Header self-pointer.** Word at `+0x0C` is `0x2C6851C0`. Under `0x2C000000` that is
   `0xFDC4` bytes **past EOF**. Under `0x2C010000` it lands on the build-info trailer.
   The BTH image behaves identically (`0x34157488`, past EOF under `0x34000000`).
2. **The image's own trailer.** Magic `0xBE57341D` @ `0x6753F4`, followed by load base
   **`0x2C010000`**, 8 bytes before EOF.
3. **Statistics.** Absolute `0x2C`-pointers landing on a push prologue: 40.6% at
   `0x2C010000` vs 4.1% at `0x2C000000`.

**Why the original audit missed it:** its spot-checks were circular — VAs were produced by
adding `0x2C000000` to a file offset, then "verified" by subtracting the same constant. BL
targets are PC-relative and validate under either base; only absolute pointer words
discriminate. `addr_audit.mjs` also has `0x2C000000` in its known-base list, so the harness
validates the convention rather than the hardware.

**Scope of damage:** all file-offset claims stay correct; all BL-derived claims stay correct.
Every absolute `0x2c…` VA in the docs is `0x10000` too low — harmless while you always convert
back by subtracting the same constant, wrong the moment you compare against a real pointer.

## 3. Wake word — claim RETRACTED

An earlier claim of mine ("the KWS model is in the OTA, ~83 KB int8 at `0xda400`–`0xf2800`")
was **refuted**. `STAR_AIR_WRITEUP.md:81` ("KWS models | not in these bins") was right.

**The real model is in the Android app**, not the firmware:
`Reverse/extracted/base/assets/fsp/res/kws_model.nn` — magic `STAR_NN V0.1.0`, architecture
**DFSMN**, 1,422,200 B, **float32**. The firmware contains **zero** occurrences of
`STAR_NN`, `DFSMN`, `Denoise`, or `fsp_`.

The firmware region is DSP `.data` (`0xDA188`–`0xF2904`) and is mostly *not* weights:
a sqrt-Hann window `sin(πn/511)` (RMS residual 1.42e-08), N=512 FFT twiddles (byte-identical
copies on **both** sides — linker adjacency, not model structure), a 40-band filterbank
descriptor, and a DRC/AGC config (−20.0, 0.6667, −40.0, −60.0, −0.8, 8.0 dB). Best hypothesis:
HiFi4 speech-enhancement coefficients.

**What still holds:** the glasses do run first-stage KWS on the HiFi4 (`[KWS - XIAOXI]`
@ `0xaf4ba`, `HIFI_KWS_NEW START.` @ `0xaf8ea`), and they emit a bare `code:7` on wake
(PROTOCOL.md:327) — so renaming the assistant downstream is free. Note `SPEECH_AQE_KWS`
@ `0xaf379` means AQE is a *framework* with KWS as one mode; do not read it as "this data is KWS".

## 4. Fonts — format fully solved

Three LVGL `lv_font_fmt_txt` faces, 6032 glyphs each, **in the OTA**.
**Read the bases from the `lv_font_fmt_txt_dsc_t` struct, never by scanning:**

| Face | struct | glyph_dsc | **glyph_bitmap** | bpp | cap |
|---|---|---|---|---|---|
| small | `0x2fd65c` | `0x31dbc4` | `0x2fd680` | 1 | 12 px |
| medium | `0x2015e8` | `0x2e2dc8` | `0x20160c` | **4** | 14 px |
| large | `0x19d0e0` | `0x1e610c` | `0x19d104` | 1 | 17 px |

```c
struct glyph_dsc {          // 16 B × 6032 = 96,512
    uint32_t bitmap_index;  // byte offset into glyph_bitmap
    uint32_t adv_w;         // advance, 1/16 px
    uint16_t box_w, box_h;
    int16_t  ofs_x, ofs_y;  // ofs_y = baseline to bitmap bottom
};
```

Bitmaps are **plain** (packed field `bitmap_format == 0`, confirmed), bit-packed MSB-first,
`w×h×bpp` bits, **no row padding**. bpp4 = two pixels/byte, high nibble first.
cmaps: 34 ranges, 20 B each; types 0/2 dense, **types 1/3 SPARSE** (count is `list_length`,
not `range_length`). Packed field at struct `+0x1C >> 16`: `cmap_num:9, bpp:4, kern_classes:1, bitmap_format:2`.

Extractor: `Reverse/firmware/extract_lvgl_fonts_v2.py` → `analysis/fonts_v2/`.

## 6. OTA security — no signature gate

MD5 transfer + MD5 post-write + A/B bank switch. **No** RSA/ECDSA/Ed25519/secp/mbedTLS/wolfSSL
in either image. Positive control: crypto *is* detectable — the SHA-256 K-table is at `0x33acc` —
so the absence is meaningful, not vacuous. (Beware naive substring searches: `conve`**`rsa`**`tion`.)

Stronger than string absence: `BATT_CIRCLE_POSTMORTEM.md` records six modified images flashed
over BLE OTA, with **v4 booting and displaying patched output**. A signature gate would have
rejected all six.

**Your real brick risk is boot-time execution order (LVGL objects created during splash),
not signing.**

## 7. Boot splash — asset CONFIRMED, code path still open

**The 144×36 wordmark at `0x3f8ff4` IS the boot/reset splash logo** — confirmed by direct
device observation (user, 2026-09-03). The resource name `power_off` is a misnomer: it is the
brand screen for *both* power transitions.

This is the one fact in this document established by observation rather than by the oracle,
and it resolved a question static analysis could not: the asset is referenced by name from
only two *shutdown* sites, so the boot path reaches it some other way — most likely by table
index rather than by the name string.

**Patching the boot logo is therefore fully unblocked:**

| | |
|---|---|
| descriptor | file `0x3f8fb4` (144×36, cf=9 IDX4) |
| palette | file `0x3f8ff4`, 64 B — green alpha ramp `(0,255,0,a)` |
| pixels | file `0x3f9034`, 2592 B = 72 B/row × 36 rows, 2 px/byte, high nibble first |
| total | 2656 B, must stay the same length |

Passive data, fixed length, no code — it cannot reproduce the v5/v6 early-boot LVGL bootloop.

**Still open (low priority):** which code draws it at boot. Ruled out with evidence:
`mmi_logo` is a factory LCD *text* test (handler `0x4eec98`, draws "UPUP"/星纪时代);
`SplashView.cpp` is the Navigation page (`[NaviPage]`), `createView` @ `0x5b394c` creates a
bare object with no image; `do_power_on_state_action` @ `0x642554` is a logging stub and
`lv_power_ui.c` has no power-on animation. Remaining candidates: pre-LVGL early boot /
JBD013 panel init (`jbd013_api.c`, `display_image` @ `0x041e6c`, `jbd4010_display`), or the
BTH/M33 image. Note the existing `analysis/jbd013/` VAs are at the old base and need
re-basing (`+0x10000`) before use.

## 8. Cross-version check (all three OTAs)

**Code base `0x2C010000` holds for all three builds.** The **data base does not** — it is
`0x3C000000 − <that build's PSRAM copy offset>` and must be derived per image:

| Version | Build string | Copy offset | Data base |
|---|---|---|---|
| 1.0.12.83 | `Flyme XR 1.0.12.83.20241231_Air_FR` | `0x283F4` | `0x3BFD7C0C` |
| 1.0.11.53 | `Flyme XR 1.0.11.53.20241126_Air_intl_FR` | `0x28350` | `0x3BFD7CB0` |
| 1.0.7.83 | `Flyme **AR** 1.0.7.83.20240612_Air_FR` | `0x282FC` | `0x3BFD7D04` |

Derive it from the boot copy table, then **validate semantically**: count descriptors whose
`data_ptr` resolves to a valid green-ramp palette. Derived bases score 176–180; the naive
`0x3C000000` scores **0** in every build. (Counting "descriptors that resolve in range"
does NOT discriminate — both bases pass that. It is a gate that cannot fail.)

### The artwork is version-independent; only offsets move

| Asset | 1.0.12.83 | 1.0.11.53 | 1.0.7.83 |
|---|---|---|---|
| MYVU wordmark (dsc / data) | `0x3f8fb4` / `0x3f8ff4` | `0x413450` / `0x413490` | `0x3b96fc` / `0x3b973c` |

All three are 144×36 IDX4, 2656 B, and the **palette and pixels are byte-identical**
(md5 `af7e3a50…`). Consequence: **locate the logo by content, not by offset.** The 2656-byte
blob occurs exactly once per image, at the offset the resource table independently names
`power_off`. A patcher built this way needs no knowledge of the flashed version.

## 9. Method note

Three of my own errors in this audit came from the same failure: **inferring structure from
coarse statistics and reporting it without reading bytes.** A 1 KB block size manufactured
three phantom region boundaries; comparing identical offsets across *different-sized* files
"proved" content had changed when it had merely moved; a zero-centered byte histogram was
treated as diagnostic when ~10 such blocks exist in this firmware.

Two of my *verification* attempts were themselves circular — checking a value against a
manifest generated from the same assumption. That is exactly how the `0x2C000000` base error
survived the previous audit. **A gate that cannot fail proves nothing.** Where possible the
oracle now renders glyphs of known shape and asserts a control case, rather than comparing
a number to itself.
